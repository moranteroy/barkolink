# Reports card alignment and recurring TRP codes

The Reports analytics grid previously aligned cards at their tops while allowing different heights. Long collection/passenger cards left empty gaps beside the shorter booking/performance cards. Analytics cards now stretch equally within each desktop row, share header/description spacing and distribution gaps, and align their summary footers. Consistent record-count badges identify each card's scope. A container query switches to one column when the actual Reports content width is below 760px, including tablet layouts where the sidebar takes screen space.

Browser fixtures checked both desktop card pairs for equal heights and aligned bottoms, the narrow-content stacking rule, chart fit, real AG Grid behavior and PDF exports at 1366, 768, 699, 700, 390 and 320px in both themes. Passenger/performance cards were inspected separately after scrolling them into view; the Ionic scroll container does not paint every off-screen area in a single oversized element screenshot. Production build/CSP checks passed. The only full-lint errors remain the two existing control-regex findings in `securityValidation.ts`.

Migration `053_shared_trp_codes.sql` changes both manual and recurring allocation to a shared PostgreSQL sequence with the existing `TRPYYYY-MMDD###` format. The date remains the Philippine creation date, as in manual trip creation. Previews do not consume codes; failed/rolled-back operations can leave gaps, and consumed values are not reused. Sequence allocation avoids introducing a transaction-wide counter lock into fleet scheduling. Daily occurrence keys still prevent duplicate or recreated edited/cancelled trips independently of their display code.

`scripts/apply-daily-trp-codes.mjs` inspects by default. Its explicit `--apply` mode backs up definitions and all DLY sailings, rejects existing DLY rows with linked bookings/advisories/campaigns, installs the allocator and renames unlinked existing codes transactionally. A mapping is saved locally and each rename is audited. In-transaction checks require every other trip field, all bookings/passengers/payments and user records to remain unchanged.

The connected project had 146 DLY trips with no linked bookings/advisories/campaigns. All 146 were renamed successfully; live verification found zero remaining DLY codes, zero blocked schedules, valid new TRP codes and a successful cron execution. The complete database suite passed; twelve focused recurring-trip tests additionally verify TRP format, preview/non-reuse behavior, private permissions and existing fleet protections.
