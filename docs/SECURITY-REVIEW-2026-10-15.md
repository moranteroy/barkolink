**Findings, ordered by priority**

1. **High — a passenger can accumulate unpaid seat holds without an account-level cap.** The reservation path in [032_staff_port_access.sql](../supabase/migrations/032_staff_port_access.sql#L399) checks seats per booking but does not limit outstanding unpaid bookings or held seats per account. [022_prevent_duplicate_reservations.sql](../supabase/migrations/022_prevent_duplicate_reservations.sql#L30) only prevents duplicates with matching passenger details. In an in-memory database with all migrations applied, a single authenticated passenger submitted two eight-person reservations with different names: both succeeded, held 16 unpaid seats, and reduced a 16-seat sailing to zero availability. No live database was touched. This demonstrates the missing aggregate limit; automated abuse and its production impact depend on deployment protections and traffic. Reservation expiry mitigates duration, but the migration default is 1,440 minutes (24 hours), configurable by the administrator. Add an atomic per-account/per-sailing unpaid-seat budget and reservation rate limit, with a business-appropriate shorter hold period. Consider bot controls for signup and booking. Persisted limits must apply to direct RPC calls, beyond the UI.

2. **Medium — the repository does not configure browser CSP or framing protection for the main application.** [vercel.json](../vercel.json#L1) contains no response security headers; [index.html](../index.html#L1) has no application CSP. This leaves an additional barrier against script injection and clickjacking unspecified. No working XSS or clickjacking attack was demonstrated, and hosting-level headers may exist outside this folder. Check deployed responses and add a tested CSP with `frame-ancestors`, `object-src`, and `base-uri`, plus `X-Content-Type-Options` and an explicit referrer policy. Account for the inline theme bootstrap, Vite legacy output, map resources, and Supabase connections before enforcing script restrictions. The exported ticket HTML already escapes dynamic text and has its own restrictive CSP. [MDN documents framing protection through the CSP response header](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors).

3. **Medium — Android backup rules do not exclude persistent sessions or sensitive WebView data.** [AndroidManifest.xml](../android/app/src/main/AndroidManifest.xml#L5) sets `android:allowBackup="true"` without `fullBackupContent` or `dataExtractionRules`. [supabase.ts](../src/services/supabase.ts#L12) persists sessions using the SDK's default storage. Backup or device transfer may therefore include sensitive app data, depending on platform and device behavior. This is a configuration risk; no APK backup was extracted. Add explicit cloud-backup and device-transfer exclusions for credentials and sensitive local data, or disable backup with platform-appropriate rules. Verify the release APK's merged manifest and actual storage locations. [Android's backup security guidance](https://developer.android.com/privacy-and-security/risks/backup-best-practices) recommends excluding sensitive data.

4. **Medium — privileged application operations have no visible MFA assurance requirement.** The SQL dispatcher uses trusted server-managed roles, and [manage-account/index.ts](../supabase/functions/manage-account/index.ts#L33) validates tokens and administrator metadata. Neither requires an MFA assurance level, and no application MFA flow was found. A valid stolen staff/admin password or session can reach privileged actions with its role. This is hardening against account compromise, not a demonstrated role bypass. Introduce staff/admin MFA enrollment and server-side assurance checks for privileged RPCs and account-management actions, with a recovery plan. Supabase dashboard account MFA is separate from MFA for application users; live enrollment/settings were not inspected. [Supabase's security guidance includes MFA assurance enforcement](https://supabase.com/docs/guides/database/postgres/row-level-security).

5. **Medium — general API resource budgets are absent from the reviewed code.** The chatbot has persisted allowance limits, but payment status/checkout and weather handlers have no comparable caller quota or explicit body-size guard. The main RPC also runs global expired-reservation processing before dispatch, including public browsing requests ([017_editable_passenger_discounts.sql](../supabase/migrations/017_editable_passenger_discounts.sql#L123)). Repeated valid requests can cause database work or provider calls; actual denial-of-service capacity was not measured. Weather caching and request coalescing reduce upstream work, and infrastructure may add external limits. Add per-user/IP rate controls, body limits, timeouts, and monitoring; keep public reads lightweight and bound cleanup batches. Auth endpoint limits do not establish equivalent limits for business RPCs. [Supabase's API security guide](https://supabase.com/docs/guides/api/securing-your-api) describes additional API controls.

6. **Low — Android FileProvider exposes unnecessarily broad path roots.** [file_paths.xml](../android/app/src/main/res/xml/file_paths.xml#L3) exposes the external-storage root and the full cache directory through `path="."`. The provider is correctly non-exported and requires URI grants, so this is not unauthenticated filesystem access. Limit it to specific app-controlled sharing subdirectories and verify every URI grant. No arbitrary-file sharing exploit was reproduced.

**Controls that passed review and testing**

- Public tables enable RLS and revoke direct browser-role access. Private-schema access and function execution are revoked; exposed privileged payment RPCs restrict execution to the service role.
- The dispatcher derives identity from `auth.uid()` and reads authoritative `auth.users.raw_app_meta_data`; editable user metadata does not grant application roles. Demotions are enforced by server checks.
- Ownership checks isolate passenger bookings, tickets, saved travelers, and notifications. Staff operations are restricted to the assigned departure port.
- PayMongo actions verify booking ownership and server-side totals. Webhooks use HMAC signatures with timestamp validation; confirmation retrieves provider records and validates currency, amount, and sandbox mode. Sandbox payments are not evidence of real-money payment readiness.
- QR tickets are checked against live database records. Ticket HTML escapes passenger text; manifest CSV guards common spreadsheet formula prefixes. Map labels use text nodes.
- Edge Functions validate user tokens inside the handlers. Their `verify_jwt=false` configuration alone does not mean they permit unauthenticated private actions. Wildcard CORS alone is also not an authorization bypass here.
